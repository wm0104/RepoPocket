# 构建后自动发布

仍然手动运行 `Build IPA`；推送不会自动消耗构建配额。完整构建成功后，独立的发布任务会自动检查版本，不需要再手动打标签。

## 准备更新

1. 在 `project.yml` 中同步提升 `MARKETING_VERSION` 和 `CURRENT_PROJECT_VERSION`，使用三段数字版本。
2. 在将要构建的提交消息中写更新内容（标题和正文）。构建成功且版本提升后，发布任务会自动读取该精确提交的完整消息作为发行说明，无需另写 `docs/releases/<版本>.md` 或单独告知助手。
3. 同步 `Packaging/control.in` 的更新记录元数据。
4. 推送 `test` 或 `main`，运行适用测试及完整构建。

## 发布规则

- 只有原仓库 `test` / `main` 的完整标准构建成功后才能进入发布；仅验证、替代界面和更新探针构建不发布。
- 与所有已公开、非预发布的三段数字版本比较，仅严格更高的版本发布；相同或更低版本跳过，不修改已有发行版。
- 只使用同一次成功构建上传的 `RepoPocket` 产物，不重新编译。发布前验证四种安装包、SHA-256、产物版本和源提交。
- 使用精确构建提交创建新标签，不移动已有标签。先上传到草稿，核实附件后才公开；同源草稿可以在重跑时续传，其他来源草稿不覆盖。
- 发行说明只取精确构建 SHA 对应的提交消息，仅裁去首尾空白，保留标题、正文与段落；不汇总历史提交、不筛选内容、不生成补充文字，也不回退到历史 Markdown 文件。首次发布与同源草稿续传使用同一规则。
- 新版本提交消息读取失败、返回 SHA 不符、消息缺失或不是非空字符串时，在写入发行版之前失败；安装包不完整、校验失败或标签指向不符时也不公开半成品。
- 写入权限只授予独立发布任务；编译与测试任务仍只有仓库读取权限。
